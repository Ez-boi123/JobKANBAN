# JobKANBAN：个人求职看板产品规格与开发交接

版本：2026-09-08。依据：当前对话中的已确认决定、项目领域词汇、已实现预览与验证记录。发生冲突时，以用户最近一次明确要求为准。

Status: ready-for-agent

已发布到项目配置的本地 Markdown 问题跟踪器。测试采用下文推荐的浏览器交互边界；已向用户提出核对，尚未收到针对测试边界的单独反馈。

## Problem Statement

个人求职者同时跟进多个公司的不同岗位，需要看清每条求职记录当前处于哪个环节、是否有待办、何时需要行动，以及已经发生过哪些进展。阶段、阶段状态、下一步行动和求职结果如果混在一起，容易把完成准备事项理解成面试结束，把收到 Offer 理解成已接受，或把长时间没有回复理解成未通过。

用户已经通过预览确定了网页看板的布局、配色和主要操作，但需要将这些决定整理成可交接的开发规格，避免下一步开发恢复已被否定的交互，或改变已确认的详情设计。

现有预览能够操作，但使用虚构数据和固定演示日期，页面刷新后修改会重置。保存设计文件不等于保存求职记录。当前规格记录已确认的产品要求；把预览升级为持久化应用的建议尚未得到单独确认。

## Solution

提供中文桌面版个人求职看板，以投递、测评、面试、结果四列呈现每个具体岗位的一次求职过程。卡片突出当前状态、轮次、下一步行动和时间；点击卡片打开带遮罩的居中详情弹窗，在同一记录中查看和维护历史。

以“下一站 NEXT STOP”为主界面视觉主题，采用用户参考截图中的清亮蓝色、冷浅灰背景及白色导航和卡片，保留路线、四站编号和票签元素。详情沿用已确认的六类阶段／结果主题，不因主界面换肤而改变。

行动处理遵循最新的简化方案：测评或面试中的“完成并待反馈”一次完成行动并更新阶段状态；进展表单选择进入待反馈后，保存时执行同样的处理。取消行动是独立按钮，只取消当前待办。用户不需要再填写“处理当前行动”选项组，也不需要经过旧的二次状态选择弹窗。

## Implementation Decisions

以下产品与交互决定来自已确认设计。模块划分为开发交接建议，不表示用户已经选定框架、数据库或部署平台。

### 领域模型及职责

- 求职记录是聚合边界：包含稳定标识、公司、岗位、城市、投递日期、薪资、渠道、岗位链接、备注、当前求职阶段及阶段状态、当前轮次、当前下一步行动、求职结果、Offer 决定、归档标记、状态进入时间、最近更新时间和变更历史。
- 一条记录只突出一项当前行动。轮次属于同一次申请；历史应能表达每轮时间、备注和结果，不能只保留最新轮次文本。
- 推荐划分看板查询与展示、记录编辑、进展与行动处理、结果与归档、视觉主题等职责。所有状态变化经同一领域入口处理，避免详情按钮与进展表单各自维护不一致的规则。
- 当前代码为浏览器内存预览；尚无已经选定的后端、数据库模式或 HTTP API 契约。不把 React、Next.js 或某个数据库当作已确认决定。

### 状态与动作契约

| 操作 | 前提与结果 | 必须保留或记录 |
| --- | --- | --- |
| 新建记录 | 公司和岗位必填；默认投递／待投递 | 与现有岗位申请独立的标识 |
| 更新进展 | 允许跳阶段、回退；进入结果必须选择结果类型 | 原阶段、原状态、变更时间及相关历史 |
| 完成并待反馈 | 当前处于测评／面试、尚未待反馈且有行动；直接完成行动并转为待反馈 | 阶段、轮次和求职结果不变；记录原行动与时间；开始新的等待计时 |
| 进展保存进入待反馈 | 目标阶段为测评／面试，且相对于原记录新进入该阶段的待反馈状态 | 有行动才记录完成；无行动不虚构完成事件；保留旧行动真实所属环节与轮次，不推断考核通过 |
| 已待反馈记录普通保存 | 同一阶段、同一待反馈状态 | 跟进行动及原等待起点；不得再次自动完成行动 |
| 其他情况下完成行动 | 投递、结果或已待反馈记录有当前行动 | 只完成待办，保留阶段、状态、轮次、结果、Offer 决定及原等待起点 |
| 取消行动 | 有当前行动；使用独立按钮 | 清理当前行动、日期和提醒；保留进展；历史明确记录取消 |
| 归档／恢复 | 结果记录可手动归档；归档记录可恢复 | 原阶段、状态、求职结果、Offer 决定与历史 |

- 完成与取消先保留原行动内容、原截止／预约时间、时间类型和轮次，再清理当前行动；处理时间与原到期时间分别记录，不互相替代。
- 行动结果至少区分完成、取消和更新，不以“消失”推断为完成。无行动时不制造完成事件，不显示可执行的完成或取消入口。
- 最新简化方案不再包含“处理当前行动”三选项，也不包含“本轮完成／仅完成准备事项”的二次选择弹窗。
- 进展表单在新进入待反馈时明确提示保存的后果，并隐藏、禁用行动输入；轮次字段保持独立。用户切回其他状态时保留先前行动草稿。
- 普通进展变更预填原行动与时间，保存后保留未编辑的信息。修改或清空既有行动时保留其历史，不伪造考核完成。
- 同一命令的 UI 提交只产生一次有效处理；当前没有行动时不能追加重复完成或取消记录。
- 用户取消或关闭未保存的进展编辑，原状态、行动和历史均不发生变化。
- 进入已投递或待反馈时记录等待起点；同状态编辑不重置起点。重新进入新的等待状态才重新计时。
- 完成行动不是进入下一求职阶段，也不是通过考核；记录 Offer 决定不会向招聘方发送任何消息。

### 查询与时间语义

- 搜索匹配公司或岗位；城市、阶段状态及行动日期筛选可以组合。列内数量反映当前筛选范围。
- 按行动日期升序排列，无日期置后；时间相同以最近更新优先。最近更新排序由新到旧。拖动不提供列内自由排序。
- 默认仅查看未归档记录；归档作为独立查看范围，可恢复。
- 日期区分“仅日期”与“日期加时间”；未填写具体时间不得在保存时丢失原时间或擅自补造时刻。
- 截止事项在时间已过且未处理时显示逾期；预约已过但进展未更新显示待更新。两种提醒不合并计数。
- 演示使用固定的 2026-09-08 与北京时间，便于复现实例；实际日常使用不能继续以该日期判断提醒。生产时钟和用户时区策略属于待开发决策，测试使用可控制的时间。

### 视觉及界面契约

- 主界面保持 JobKANBAN 名称与“下一站 NEXT STOP”主题。参考截图取样色为主蓝色 `#3468e8`、冷浅灰背景 `#f8f9fc`、浅蓝选中背景 `#edf3ff`，导航及卡片为白色。
- 路线插画、四站编号和票签式卡片只承担视觉识别，不添加业务含义或挡住操作。
- 四列在桌面可辨识；约 30 条记录通过滚动访问，不通过不断缩小正文挤进首屏。
- 点击卡片使用屏幕中央详情弹窗，保留遮罩、关闭入口、内部滚动和 Esc 行为；不恢复右侧抽屉方案。
- 详情主题按当前阶段或结果映射：投递 `#245dcc`、测评 `#a65b08`、面试 `#7542c5`、Offer `#157653`、未通过 `#a54465`、主动退出 `#526174`。
- 详情用颜色和明确文字共同突出状态。待反馈保留所属阶段色；逾期与预约待更新在日期处单独提示；归档只叠加灰色横条，保留原结果主题。
- 主界面换肤不得改动已确认的详情和表单本体。对照检查隔离看板背景，比较面板尺寸、字体、颜色和操作位置。
- 使用当前 13 个预览状态作为视觉验收基线：主看板、岗位详情、新建、编辑、进展更新、Offer、归档与恢复、空看板、无结果、表单错误、结果必填、进入待反馈的简化进展、完成后的待反馈详情。

## Testing Decisions

### 推荐的主要测试边界

沿用现有浏览器交互测试，以用户可操作的网页作为主要测试边界。通过新建、打开详情、选择状态、保存、完成行动、取消行动和归档等入口，检查最终卡片、详情、提醒及可见时间线的结果。优先从这一条完整使用链路验收，不按每个组件或函数另造测试边界。

好的测试检查用户可观察的行为及规则，不绑定内部函数名、DOM 层级或状态存储形式。当前预览检查中存在用于取样的内部数据读取；正式开发应优先以可见历史和公开行为断言，避免将调试接口当作长期产品契约。必要时用少量领域边界检查补足 UI 无法观察的原时间保留或命令去重，不重复整套浏览器场景。

### 覆盖范围

1. 记录管理：新建必填项、默认状态、编辑预填、错误时保留输入、同公司不同岗位独立。
2. 阶段流转：拖动后保存／取消、跳过或返回阶段、结果必选、轮次保留。
3. 行动处理：详情直接完成并待反馈、进展保存进入待反馈、独立取消、其他阶段完成、无行动及重复操作。
4. 关键反例：已待反馈记录的跟进行动不被普通保存完成；取消行动不改变状态；完成 Offer 待办不替用户作决定；跨阶段不凭空产生通过结论。
5. 历史及时间：原行动、日期类型、预约／截止时间、轮次、完成／取消语义和实际处理时间正确；更新与清理反映到详情、卡片、提醒和筛选。
6. 查询及结果：搜索和组合筛选、无结果清除入口、两种排序、Offer 三种决定、手动归档与恢复。
7. 界面回归：居中弹窗及层级关闭、内部滚动、两档桌面宽度、13 个关键状态、六类详情主题以及主界面换肤不影响详情。

### 已有测试先例与证据边界

- 现有浏览器检查涵盖 9 项基础流程、16 项简化行动流程、10 项居中交互及 12 项详情主题检查。
- 最近的主界面配色更新通过 8 项边界检查：6 个详情／表单面板单体对照一致，以及 1440、1200 像素宽度的指定内容适配。
- 这些检查分布于不同迭代，存在重叠，不应把数量相加当成独立验收项或声称每次修改全部重跑。
- 现有测试验证的是固定样例的本地预览，不验证数据持久化、真实时钟、跨设备同步、网络异常或 Figma 原生可编辑性。
- 持久化若在后续单独确认，优先扩展同一浏览器边界：保存后刷新与重新打开仍有数据、失败不显示成功、历史与当前状态一致。不在本规格中预先选定其存储实现。
